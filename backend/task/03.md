# Template de Prompt para Criar uma Rota de API

## Objetivo

Implementar a rota **`GET /home/:date`** que devolve, para o **usuário autenticado**, o payload necessário para montar a **página inicial** do app (plano ativo, dia de treino referente à data solicitada, streak e consistência semanal).

## Stack e arquitetura (obrigatório)

Seguir `.codex/rules/architecture.md`:

- Rota em `src/routes`, sem regra de negócio — apenas validação Zod v4 (`fastify-type-provider-zod`), sessão e chamada ao use case.
- Use case em `src/usecases` com as regras de domínio; erros customizados em `src/erros/index.ts` e mapeamento HTTP na rota (`schema.response` para todos os status relevantes).
- Autenticação: `auth.api.getSession` + `fromNodeHeaders` como nas rotas existentes.
- Schemas compartilhados / resposta de erro: `src/schemas/index.ts`.
- **Datas:** usar **dayjs** para parsing, comparação e formatação (intervalo da semana em UTC, `weekDay`, etc.).

## Contrato da rota

| Aspecto | Detalhe |
|--------|---------|
| Método | `GET` |
| URL | `/home/:date` |
| Proteção | Sim — sem sessão → `401` |

### Params

- `date`: string no formato **`YYYY-MM-DD`** (validar na rota com Zod, por exemplo `z.string().regex(/^\d{4}-\d{2}-\d{2}$/)` ou equivalente que garanta calendário válido).

### Body / Query

Nenhum.

### Responses esperadas

- **`200`**: payload descrito abaixo.
- **`401`**: não autenticado (`ErrorSchema` / padrão do projeto).
- **`404`**: quando não existir **workout plan ativo** para o usuário (ou outro recurso obrigatório ausente — definir código/mensagem no use case e documentar na rota).
- **`500`**: erro não tratado.

Documentar `tags` e `summary` no `schema` da rota.

## Payload de sucesso (`200`)

```ts
interface HomeResponse {
  activeWorkoutPlanId: string;
  todayWorkoutDay: {
    workoutPlanId: string;
    id: string;
    name: string;
    isRest: boolean;
    weekDay: string;
    estimatedDurationInSeconds: number;
    coverImageUrl?: string;
    exercisesCount: number;
  };
  workoutStreak: number;
  consistencyByDay: {
    // Chave: "YYYY-MM-DD" — todos os 7 dias da semana (domingo a sábado), UTC.
    // Dias sem sessão ainda assim aparecem com workoutDayCompleted/workoutDayStarted adequados.
    [dateKey: string]: {
      workoutDayCompleted: boolean;
      workoutDayStarted: boolean;
    };
  };
}
```

**Notas de modelagem**

- `todayWorkoutDay` refere-se ao **dia de treino do plano ativo** cuja data de calendário corresponde ao **`date` recebido no path** (não necessariamente “hoje” no relógio do servidor).
- `weekDay`: formato esperado alinhado ao restante da API (ex.: nome abreviado ou índice — **padronizar com os modelos/`WorkoutDay` existentes**).

## Regras de negócio

### Semana em UTC

A partir do `date` informado:

1. Calcular o **domingo** (início) e o **sábado** (fim) da semana que contém essa data, **em UTC**.
2. Intervalo inclusivo para sessões: do **domingo 00:00:00.000 UTC** ao **sábado 23:59:59.999 UTC** (ou equivalente sem ambiguidade de fuso — documentar na implementação).

### Treino do dia (`todayWorkoutDay`)

1. Obter o **workout plan ativo** do usuário.
2. Entre os dias desse plano, resolver o dia de treino cuja **data** coincide com o **`date`** da rota (mesma convenção de “qual dia do plano cai nesse calendário” já usada no domínio).

Se não houver plano ativo → erro mapeado para **`404`** (ou o código que o projeto adotar para “sem plano ativo”).

### `workoutStreak`

Número de **dias consecutivos** em que o usuário **completou** pelo menos um dia de treino relevante ao plano (incluir na definição **dias de descanso** quando o produto considerar que completar o “dia” de descanso conta para consistência — **manter alinhado ao exemplo**: se o plano tem segunda–quinta e o usuário completou todos os dias planejados incluindo descansos entre eles, o streak reflete essa sequência).

Requisitos para o implementador:

- Deixar explícito no código **o que conta como “dia completado”** (ex.: só dias com `completedAt` em sessão associada ao plano/dia).
- Definir comportamento quando **não há sessões** ou **buracos na sequência** (streak reinicia em zero ou no último bloco contínuo — **especificar de forma determinística**).

### `consistencyByDay`

1. Buscar todas as **`WorkoutSession`** do usuário cujo `startedAt` cai **dentro** do intervalo semanal UTC acima.
2. Agrupar por **data calendário UTC** derivada de `startedAt` (apenas a parte data, `YYYY-MM-DD`).
3. Para cada uma das **7 chaves** da semana (domingo → sábado), preencher:
   - Se existir sessão **com `completedAt` preenchido** para aquele dia: `workoutDayCompleted: true` e `workoutDayStarted: true`.
   - Se existir sessão **somente iniciada** (`completedAt` ausente): `workoutDayStarted: true`, `workoutDayCompleted: false`.
   - Se **várias sessões** no mesmo dia: a regra deve ser **determinística** (ex.: completed ganha de started; ou merge OR — **documentar na implementação**).

## Checklist para quem implementa

- [ ] Zod v4 nos params e no `response`; erros tipados.
- [ ] Use case testável (dependências injetáveis ou construtor alinhado aos outros use cases).
- [ ] Testes ou exemplos manuais cobrindo: sem plano ativo, semana limite UTC (domingo/sábado), dia com sessão só iniciada vs completa.
