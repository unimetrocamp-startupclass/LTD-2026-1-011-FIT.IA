# Refatoração de Use Case — Tratamento de WorkoutPlan Opcional

Este documento descreve as diretrizes e requisitos para a refatoração do `src\usecases\GetHome.ts`, com foco em tornar o fluxo resiliente à ausência de `workoutPlan`, mantendo performance, arquitetura e qualidade de código.

## Requisitos de Refatoração

A refatoração deve seguir rigorosamente as regras do projeto descritas nos seguintes documentos em `.codex`:

- `.codex\rules\architecture.md`
- `.codex\rules\typescript.md`
- `.codex\rules\general.md`

## Problema Principal a Corrigir

### Uso de Fail Fast Incorreto para Regra de Negócio

Atualmente o código lança erro quando não existe um `workoutPlan` ativo:

```typescript
if (!workoutPlan) {
  throw new NotFoundError("Active workout plan not found");
}
```

Isso transforma um cenário válido de negócio em erro técnico.

### Comportamento Esperado

A ausência de `workoutPlan` deve ser tratada como um estado válido do sistema.

## Regras Obrigatórias de Implementação

### Tornar `workoutPlan` Opcional no Fluxo

- Remover completamente o `throw NotFoundError`
- O fluxo deve continuar normalmente mesmo sem plano

### Ajustar o `OutputDto`

Alterar obrigatoriamente:

```typescript
activeWorkoutPlanId: string;
```

Para:

```typescript
activeWorkoutPlanId?: string;
```

### Garantir Segurança de Acesso

Todo acesso a `workoutPlan` deve ser protegido:

Proibido:

```typescript
workoutPlan.id;
```

Obrigatório:

```typescript
workoutPlan?.id;
```

ou validação explícita antes do uso.

### Definir Comportamento Sem `WorkoutPlan`

Quando `workoutPlan` for `null` ou `undefined`, o retorno deve ser:

```json
{
  activeWorkoutPlanId: undefined,
  todayWorkoutDay: undefined,
  workoutStreak: 0,
  consistencyByDay: {
    [date]: {
      workoutDayCompleted: false,
      workoutDayStarted: false
    }
  }
}
```

### Consistência Semanal Deve Continuar Existindo

Mesmo sem `workoutPlan`, `consistencyByDay` deve:

- Retornar exatamente 7 dias
- Baseado na semana da `currentDate`
- Todos os valores como `false`

### Evitar Queries Desnecessárias

Quando não houver `workoutPlan`:

Não executar:

- `query` de `workoutSession`
- cálculo de `streak` dependente de banco

O retorno deve ser gerado localmente

### Preservar Otimizações Existentes

Mesmo com a mudança:

- Manter uso de `Map` para agrupamentos
- Manter complexidade `O(n)`
- Não reintroduzir `filter` dentro de `loop`
- Não reintroduzir `overfetch`

### Manter Separação de Responsabilidades

Funções privadas devem continuar sendo usadas para:

- agrupar sessões
- calcular consistência
- calcular `streak`
- mapear dias da semana

### Datas Devem Permanecer em UTC

- Uso obrigatório de `dayjs.utc`
- `startOf("week")` e `endOf("week")`
- Formato padrão: `"YYYY-MM-DD"`

### Padrão Obrigatório de Early Return

Adicionar um `early return` explícito:

```typescript
if (!workoutPlan) {
  return {
    activeWorkoutPlanId: undefined,
    todayWorkoutDay: undefined,
    workoutStreak: 0,
    consistencyByDay: buildEmptyConsistency(currentDate),
  };
}
```

### Criar Função Auxiliar Obrigatória

`private buildEmptyConsistency(currentDate: dayjs.Dayjs): OutputDto["consistencyByDay"]`

Responsável por:

- gerar os 7 dias da semana
- preencher todos com `false`

## Restrições

X Não alterar regras de negócio existentes
X Não alterar estrutura geral do `use case`
X Não simplificar arquitetura
X Não adicionar dependências
X Não alterar nomes de métodos existentes (exceto quando necessário)

## Resultado Esperado do Codex

O Codex deve devolver:

- Um único arquivo de `use case` refatorado
- `workoutPlan` tratado como opcional
- Nenhum erro sendo lançado por ausência de plano
- `OutputDto` ajustado corretamente
- Zero `queries` desnecessárias
- Algoritmos eficientes (`O(n)`)
- Código seguro contra `undefined`
- Código pronto para produção
