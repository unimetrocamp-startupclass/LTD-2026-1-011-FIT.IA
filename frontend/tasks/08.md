# Template de Prompt para Resolver state_mismatch no OAuth Google

## Objetivo

Corrigir o erro **`?error=state_mismatch`** que ocorre após o redirect de login com Google, causado por **cookies de sessão OAuth bloqueados pelo browser** em fluxos cross-domain entre frontend e backend hospedados em subdomínios distintos do `onrender.com`.

## Stack e contexto (obrigatório)

- **Auth:** `better-auth` no backend (Fastify)
- **Frontend:** Vite / React hospedado na Render como Static Site
- **Problema:** frontend (`app.onrender.com`) e backend (`api.onrender.com`) estão em origens diferentes; o cookie com o `state` do OAuth é criado no backend mas **não enviado de volta** no callback porque o browser bloqueia cookies cross-domain sem configuração adequada
- **Restrição:** sem domínio customizado disponível — solução via **proxy**

## Diagnóstico

| Sintoma | Causa raiz |
|---|---|
| `?error=state_mismatch` na URL após login | Cookie `state` não lido no callback |
| Cookie ausente nas DevTools no callback | Browser bloqueou por política `SameSite` |
| Funciona em `localhost` mas não em produção | Em dev, tudo é mesma origem (`localhost`) |

O fluxo OAuth gera um `state` aleatório, salva em cookie e valida no callback. Se o cookie não trafega, a validação falha.

## Solução: Proxy no Frontend

Fazer o frontend **proxiar** todas as rotas `/api/auth/*` para o backend. Assim, para o browser **tudo é a mesma origem** — sem cookie cross-domain, sem problema.

### 1. Desenvolvimento — `vite.config.ts`

```typescript
export default defineConfig({
  server: {
    proxy: {
      "/api/auth": {
        target: env.VITE_API_BASE_URL, // ex: http://localhost:3333
        changeOrigin: true,
      },
    },
  },
});
```

### 2. Produção — `public/_redirects`

Criar o arquivo `public/_redirects` na raiz do projeto frontend:

```
/api/auth/*  https://seu-backend.onrender.com/api/auth/:splat  200
```

A Render processa esse arquivo automaticamente em Static Sites e faz o rewrite server-side.

### 3. Cliente better-auth

Ajustar a `baseURL` do cliente para usar a rota local (proxiada), não o endereço direto do backend:

```typescript
// src/lib/auth-client.ts
export const authClient = createAuthClient({
  baseURL: "/api/auth", // ← rota local, não o backend diretamente
});
```

### 4. Backend — `auth.ts`

Remover ou simplificar o `crossSubDomainCookies` (não é mais necessário com proxy):

```typescript
export const auth = betterAuth({
  baseURL: env.API_BASE_URL,
  trustedOrigins: [env.WEB_APP_BASE_URL],
  socialProviders: {
    google: {
      prompt: "select_account",
      clientId: env.GOOGLE_CLIENT_ID,
      clientSecret: env.GOOGLE_CLIENT_SECRET,
    },
  },
  database: prismaAdapter(prisma, { provider: "postgresql" }),
  plugins: [openAPI()],
  // crossSubDomainCookies não necessário com proxy
});
```

## Checklist para quem implementa

- [ ] `public/_redirects` criado e commitado no repositório frontend
- [ ] `vite.config.ts` com proxy apontando para a variável de ambiente correta
- [ ] `authClient` usando `/api/auth` como `baseURL` (sem URL absoluta do backend)
- [ ] Variável `VITE_API_BASE_URL` configurada no ambiente de dev
- [ ] Testar em dev: login completa sem `state_mismatch`
- [ ] Verificar nas DevTools (Network) que o callback de `/api/auth/callback/google` bate no próprio frontend e é reescrito — não no backend diretamente
- [ ] Deploy na Render: confirmar que o `_redirects` está na pasta de output do build (`dist/`)

## Observações

- O arquivo `_redirects` deve estar na pasta de **saída do build** (`dist/`). Se estiver apenas em `public/`, confirmar que o Vite copia `public/` para `dist/` (comportamento padrão).
- Essa abordagem elimina a necessidade de `SameSite: none`, `Secure`, ou domínio compartilhado — é a solução mais simples e segura para o contexto sem domínio próprio.
- Caso no futuro seja adicionado um domínio customizado, remover o proxy e voltar para `crossSubDomainCookies` com `.seudominio.com`.
